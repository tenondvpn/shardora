## 三、为什么「100 Token / 5000 AMM 对 / 10 万用户」是一个极端压力测试

### 3.1 交易量估算

```
10 万用户 × 日均 10 笔 DeFi 操作 = 100 万笔/天 ≈ 11.6 TPS（基准）
市场波动高峰期 × 50 倍 = 580 TPS（单 App 峰值）

加上：套利机器人 × 5000 对 × 每对每秒 N 笔 MEV 抢跑
→ 瞬时峰值轻易超过 5,000–10,000 TPS（仅这一个应用）
```

**以太坊结论**：整条链 15–30 TPS，这一个应用的基准负载就能让整条链拥堵，gas 飙升至不可用。

**Solana 结论**：2023–2024 年 Meme 币潮期间，Solana 多次在 DeFi 高峰期完全宕机，正是因为单链架构在高并发 AMM 负载下无法线性扩容。

### 3.2 5000 个交易对的组合爆炸问题

100 个 TOKEN 生成 `C(100,2) = 4,950` 个交易对。典型 DEX 路由场景：

```
用户想将 TokenA 换成 TokenZ（无直接流动性池）
→ 路由：A→WETH→USDC→Z（3 跳）
→ 涉及 3 个池，必须原子执行
```

**跨分片 3 跳原子性**，在任何其他分片架构中都是未解问题：
- Near：每一跳跨分片都要等 1–2 个额外区块，3 跳 = 4–6 秒，且无法保证原子
- Harmony：跨分片通过中心化 Bridge，已被攻击证明不安全
- 以太坊 L2 Rollup：跨 Rollup 原子性至今无标准方案

**Shardora 的解法（已工程实现）**：

```
deploy_address = keccak256(0xff || sender || salt || keccak256(bytecode))[-20:]
pool_index     = Hash32(deploy_address) % kImmutablePoolSize

→ 同一部署者的所有合约（AMMPool + TokenA + TokenB）
  → 相同 pool_index → 同一共识池内执行
  → EVM CALL 指令解析为 intra-pool 调用
  → 三个合约状态变更在单个共识轮次内完成
  → 完全原子，无补偿交易
```

源码位置：[src/common/utils.h](src/common/utils.h)（`GetAddressPoolIndex`）、[src/shardoravm/shardora_host.cc](src/shardoravm/shardora_host.cc)（intra-pool EVM CALL）

## 四、Shardora 独有的技术组合——为什么「抄」不了

### 4.1 高 TPS × 真去中心化 = 矛盾项

**传统 BFT 共识**：O(n²) 消息复杂度，实际可用节点上限约 200。

Solana、Sui、Aptos 都选择了牺牲去中心化（100–1,500 验证者）来换 TPS。
以太坊选择了去中心化（100 万质押者）但放弃了 TPS。

**Shardora 的解法**：BLS 门限聚合签名将每分片委员会通信复杂度从 O(n²) 压缩到 **O(1)**。

```
1000 个委员会节点签名 → 1 个聚合 BLS 签名（96 字节）
验证者接收 1 个证书，不管委员会有多大
→ 5000 节点 / 4 分片 ≈ 每分片 1250 节点 → 依然 O(1) 验证
```

论文支撑：Akaverse (IEEE TDSC)，BLS 门限共识章节。

### 4.2 换届不停机 = Shardora 独有

**所有分片链都有的问题**：节点换届（epoch rotation）时，新旧委员会密钥切换导致 TPS 归零窗口（Zero-TPS Gap）。

对于 DeFi 场景：
- 换届期间无法出块 → 套利机器人堆积 → 换届结束后瞬间拥堵
- 持仓用户无法在换届期间止损 → 价格波动时流动性枯竭

**Shardora 方案（CCS 2025 / TNSE 2026）**：

```
共识委员会（当前）────────────────▶ 继续处理交易
等待委员会（下届）──同步状态──▶ 准备好后无缝接管

并行 DKG 密钥协商：下届密钥在上届运行期间预生成
密钥复用优化：90%+ 开销削减

→ TPS 曲线全程平滑，换届期间无任何中断
```

**目前没有任何其他分片区块链实现了这一点。**

### 4.3 <2 秒确认 × 1000+ 节点/分片

大多数 BFT 协议在 200+ 节点时延迟爆炸（leader 等待所有副本响应）。

**Shardora 的 EVS（增强视图同步）**：

```
传统流程：leader 等待 2/3 节点 → 消息往返 O(n) 次 → 延迟随 n 线性增长
EVS 流程：门禁规则 → 只有持有当前视图 QC 的副本才能提交
         → BLS 聚合 → leader 收到 1 个聚合证书即可推进
         → 延迟与节点数解耦
```

实测：1024 副本，<10 秒 端到端延迟（含网络传播），**单分片 <2 秒出块确认**。

### 4.4 跨分片 DeFi 无回滚（SCoRE · SOSP 2026）

当 AMM 路由必须跨分片时（用户来自 Shard A，某个 Token 合约在 Shard B），需要跨分片结算。

**现有方案的失败模式**：
- 乐观执行：Shard A 已扣款，Shard B 执行失败 → 回滚传播 → 全链状态不一致
- 悲观锁：等待所有分片确认 → 串行化 → TPS 退化为单链水平

**SCoRE 预存款模型**：

```
1. Prefund   ── Root Shard 锁定资金（原子）
2. Execute   ── 各分片独立执行，生成执行证明（并行）
3. Settle    ── 携带证明的跨分片结算消息（无需全局锁）
4. Refund    ── 多余 Gas 退回（原子）

→ 无全局锁，无回滚传播，服务调用与资金转移解耦
→ SCoRE-4P（4 并行池）吞吐量 ≈ 单池 3 倍
```

### 7.1 跨链桥攻击史：反面教材

历史上最大的几次加密货币盗窃全部发生在跨链桥上：

| 事件 | 损失 | 根本原因 |
|------|------|----------|
| Ronin Bridge (Axie) | $625M | 多签私钥被窃，验证者作恶 |
| Wormhole | $320M | 签名验证逻辑漏洞，伪造 VAA |
| Poly Network | $611M | 合约特权函数被外部调用 |
| Harmony Horizon | $100M | 2-of-5 多签门限过低，私钥被攻破 |

**共同根因**：这些桥依赖「受信任的中继者」或「多签管理员」——一旦私钥泄露，攻击者可以无限增发目标链代币。

Shardora 的方案从根上消灭了这一假设。

### 7.2 核心创新一：160-bit 恒等锚定 Feistel 双射地址派生

**问题**：在分片链上，如何证明 Shard B 上的某个合约是 Shard A 上某合约的「真实分身」，而不是攻击者伪装的合约？

**传统方案**：跨链桥维护一张「白名单映射表」，由管理员多签写入。→ 管理员私钥泄露 = 攻击者可以注册任意伪造映射。

**Shardora 方案**：

```
派生地址 = Feistel_Permutation(BaseAddress, shardId, poolId)
逆向验证 = Feistel_Inverse(ShardAddress, shardId, poolId) → 还原出 BaseAddress
```

4 轮 Feistel 网络在 160 位地址空间上构成**严格双射置换（SPRP）**：
- 给定任何分片地址，O(1) 无查表反算出根地址
- `(0, 0)` 坐标为恒等锚定：根分片地址与 BaseAddress 完全相同，无需映射
- EVM 20 字节满熵保持，与以太坊生态完全兼容

**安全结论**：攻击者在目标分片上伪造一个「假分身合约」，其地址经 Feistel 逆算后得到的 BaseAddress 与真实合约不同，共识层在派发系统调用前强制断言：

```
RecoverBase(target_addr) == RecoverBase(src_addr)  // 不等则拒绝
```

**无需任何白名单、无需管理员、无需多签。数学本身就是安全。**

### 7.3 核心创新二：内生零铸造分身合约（构造函数自鉴权）

分身合约（跨分片部署的代币镜像）在**构造函数**里执行：

```solidity
address recoveredBase = address(this).recoverBaseAddress(shardId, poolId);
if (shardId == 0 && poolId == 0 && recoveredBase == address(this)) {
    IS_ROOT = true;
    totalSupply = initialSupply;  // 只有根合约可铸币
} else {
    IS_ROOT = false;
    totalSupply = 0;              // 所有分身：绝对零初始供应
}
```

**含义**：
- 合约一旦部署，`IS_ROOT` 和 `totalSupply = 0` 被写入不可变存储（`immutable`）
- 不存在 `mint()` 函数可以被攻击者调用
- 分身代币的唯一入账途径是 `systemExecuteCrossTransfer`（只有共识层的 `SYSTEM_EXECUTOR` 能调用）
- **即使攻击者拿到了合约 ABI，也找不到任何铸币入口**

这是历史上所有跨链桥漏洞的数学级根治：**不存在可被攻击的铸币面**。

### 7.4 核心创新三：阿贝尔群建模——跨分片转账无需分布式锁

这是最精妙的代数洞察：

**传统跨分片转账的困境**：
- A 分片扣款 → 消息在途 → B 分片收款
- 如果网络乱序，两个并发转账到达顺序不确定，用传统方式需要加锁排队

**Shardora 的洞察**：代币余额的更新是**加法**，加法在整数上满足**交换律**：

```
T_Δ1 ∘ T_Δ2(B) = (B + Δ2) + Δ1 = (B + Δ1) + Δ2 = T_Δ2 ∘ T_Δ1(B)
```

**推论**：不管两笔跨分片转账以何种顺序到达，最终余额严格相同。

因此：
- **零分布式锁（Lock-Free）**：不需要 2PC 协议，不需要等待确认
- **强最终一致性（SEC）**：网络抖动、消息乱序，状态自动收敛
- **零回滚级联**：目标端入账操作唯一可能失败的情况（溢出）在数学上不可能发生

这一性质是 Solana、Near、Polkadot **都没有显式建模和证明的**，是 Shardora 独有的形式化基础。

### 7.5 核心创新四：非可交换金融状态的算法级隔离

AMM 的恒定乘积公式 `(x+Δx)(y-Δy) ≥ k` 是**非可交换的**——执行顺序影响滑点。这是跨分片 DeFi 最难的问题。

**错误方案（其他链的教训）**：
- 把 AMM 合约迁移到「交叉分片」执行 → 滑点不确定、状态竞争、穿仓
- 用分布式锁串行化 AMM 操作 → TPS 退化回单链水平

**Shardora 的方案**：

```
非可交换操作（AMM计算）──────→ 严格封闭在单个分片池内，单机 SMR 即时收敛
可交换操作（代币转账）  ──────→ 阿贝尔群加法，跨分片无锁流动
                               ↑
                         两者正交解耦，互不干扰
```

**对 5000 AMM 对的具体含义**：
- 同一部署者的 TokenA + TokenB + AMMPool → 通过 CREATE2 地址派生，**自动共置于同一分片池**
- 池内 AMM 计算完全原子（单轮共识）
- 跨池套利通过阿贝尔转账原语连接，无锁，无滑点竞争
- 100 个 Token，5000 个池，全部并行运行，互不阻塞
