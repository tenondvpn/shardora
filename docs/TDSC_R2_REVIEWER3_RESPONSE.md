## 问题一：Gap-Aware 同步、跨窗口排序与最终确认延迟

### 审稿人关切

> 1. Gap 同步机制的阻塞行为可能影响事务最终确认延迟和系统性能。
> 2. Lemma A4 的排序论证不够形式化：当源 pool 的两条记录 $r_1 \prec_{\mathrm{src}} r_2$ 因网络延迟分别落入不同 GBP 窗口 $W_t$ 与 $W_{t+1}$ 时，协议如何保证跨窗口的词典序/源序得到保持？

### 回应

#### 1.1 跨窗口源序保证的形式化

Akaverse 的 GBP 排序保证建立在**高度严格单调约束**上，而非依赖消息的到达顺序。以下给出精确化的论证。

**协议不变量（Protocol Invariant）**：设源 pool $P_i$ 在 GBP 批次 $W_t$ 中承诺的最高块高度为 $H_i^t$，则 GBP Leader 在提议 $W_{t+1}$ 时，必须满足：

$$H_i^{t+1} > H_i^t \quad \text{（严格单调，实现于 } \texttt{LeaderCreateToHeights()}\text{）}$$

**跨窗口因果序保证**：设 $r_1$ 来自源 pool $P_i$ 的块高 $h_1$，$r_2$ 来自块高 $h_2 > h_1$。

- **情形 A（正常传播）**：$r_1, r_2$ 均在 $W_t$ 到达 GBP。GBP 在批次 $W_t$ 中按高度范围 $[H_i^{t-1}+1, H_i^t]$ 聚合，且 $h_1 < h_2 \le H_i^t$，故 $r_1$ 与 $r_2$ 在同一批次中按高度升序排列——源序保持。

- **情形 B（$r_2$ 超前到达）**：$r_2$ 在 $W_t$ 到达，而 $r_1$（对应 $h_1 < h_2$）所在的块尚未被 GBP 观测到。此时，由于单调约束，GBP 的高度上界 $H_i^t$ **不能超过已连续确认的最高高度**——即 $H_i^t < h_1$。因此 $r_2$ **无法被纳入** $W_t$，而是停留在缓冲区 `network_txs_pools_[i][h_2]`，等待 $h_1$ 所在块被 Gap 同步拉取并确认后，在 $W_{t+k}$（$k \ge 1$）中才能被聚合。

**结论**：无论 $r_2$ 何时到达，只要 $r_1$ 对应的块高尚未被 GBP 纳入批次，$r_2$ 就不会被提前处理。这在协议层面保证了跨窗口的源序不变量，Lemma A4 的正确性由此得到严格支撑。我们将在修订稿中补充以下形式化命题：

> **Lemma A4'（精化）**：对于来自同一源 pool $P_i$ 的任意两条跨池记录 $r_1$（高度 $h_1$）和 $r_2$（高度 $h_2 > h_1$），在部分同步网络模型下，若 Akaverse GBP 协议遵守严格单调约束，则存在 GBP 批次 $W_s \le W_t$ 使得 $r_1 \in W_s$ 且 $r_2 \in W_t$（$s \le t$），即 $r_1$ 的跨池效果在 $r_2$ 之前或同一批次中被目标 pool 处理，源序得到保持。

#### 1.2 Gap 同步对延迟和吞吐量的影响

**性能代价分析**：在部分同步模型（GST 后消息延迟上界为 $\Delta$）下：

- 正常路径（无 Gap）：GBP 批次延迟 = 一次 Fast-HotStuff 共识轮次时间，约 300–500 ms，与常规 pool 相当。
- Gap 路径：额外延迟 = 拉取缺失块的时间，上界为 $k \cdot \Delta$（$k$ 为缺失块数）。一旦缺失块到达，GBP 立即恢复正常提议节奏；缓冲期间常规 pool 的 TPS **不受影响**（GBP 与常规 pool 并行运行）。

**吞吐量不受全局阻塞**：关键性质是 Gap 同步仅阻塞**涉及该缺失高度之后**的 kNormalTo 批次，不会暂停常规 pool 的本地共识。因此，整体吞吐量下降仅限于跨池事务的最终确认延迟，而非系统级停顿。

## 问题二：全跨池压力测试未能孤立 GBP 协调代价

### 审稿人关切

> 1. 压力测试与主吞吐量对比使用不同配置，无法直接比较以识别 GBP 引入的增量开销。  
> 2. 32-pool 结果缺少关键配置参数（GBP 委员会大小、委员会重叠情况、跨池事务流分布）。  
> 3. 建议以"变化跨池事务比例"的受控实验直接测量 GBP 协调代价。

### 回应

#### 2.1 关键澄清：全局感知是路由效率与预验证的必要条件，而非可选安全特性

我们需要首先澄清 GBP 全网感知机制的设计动机，以说明为何"跨池事务比例"在 Akaverse 中不是一个可调节的实验变量。

**在 Akaverse 中，GBP 全网共识是所有价值转移事务的必经路径，与发送方和接收方是否归属同一 pool 无关。** 即使 $A$ 和 $B$ 在同一 pool 内，$A \to B$ 的转账同样必须经过 GBP 批次提交，形成全网所有分片可验证的最终态。

这一设计的核心动机在于**维护全局地址状态索引**，而非单纯出于防双花目的：

**动机一（跨分片直接路由）**：在多分片架构中，当用户 $A$（位于 Shard $X$）向用户 $B$（位于 Shard $Y$）发起转账时，发起方节点需要知道 $B$ 所在的分片，才能将交易直接路由到目标分片 $Y$，而无需经过 root shard 中转。若某笔转账的余额变更仅在本 pool 内完成而不经 GBP 全网广播，其他分片的节点将无法获知该地址的分片归属，导致后续跨分片转账需额外经过 root shard 共识确定归属后再转发，引入不必要的额外共识轮次。GBP 的全网共识使每个节点都能维护一份完整的全局地址-分片索引，实现**跨分片转账的直接路由**。

**动机二（发起方预验证，拒绝无效请求）**：当用户提交一笔转账时，接收该请求的节点在本地查询 from 地址余额完成合法性验证，若余额不足则立即拒绝请求，避免无效交易进入共识流程消耗网络资源。若节点同时能从 GBP 维护的全局地址索引中本地确认 to 地址的分片归属，则可以直接将交易投递至正确的目标分片。若缺少全局地址索引，节点无法在本地确认 to 地址的归属，需在本分片共识后将交易发送至 root shard，由 root shard 共识确定归属后再转发目标分片，增加额外的共识开销和网络负担。

**动机三（全局一致性保证）**：上述两个功能目标共同要求所有余额变更必须形成全局可见的最终态，使全网任意节点在任意时刻都能基于一致的地址状态做出正确的路由和验证决策。

因此，"跨池事务比例"在 Akaverse 中不是一个有意义的实验变量——所有价值转移事务的 GBP 参与率恒为 100%，与地址的 pool 分布无关。审稿人所建议的"变化跨池比例"实验，其隐含前提（存在不经 GBP 的价值转移快速路径）在 Akaverse 中根本不成立。若绕过 GBP，跨分片到账的完整处理流程如下：节点首先本地查询 from 地址余额完成合法性验证，合法则将交易转发至目标分片；对于 to 地址的跨分片到账，若本地无法查到 to 地址的目标分片归属，则需在本分片共识后将交易统一发送至 root shard——root shard 对新地址需共识分配 shard 并新建地址后转发至目标分片，对已知地址则直接共识转发——目标分片收到后再次共识累加余额。整个过程涉及**源分片共识 → root shard 共识 → 目标分片共识**三轮跨分片协调，大幅增加确认延迟和网络负担。GBP 的全网感知机制正是为了消除这一复杂路径：通过 GBP 维护全局地址-分片索引，使跨分片转账能够直接从源分片路由到目标分片完成到账，无需经过 root shard。

我们将在修订稿的系统设计节中明确陈述这一设计约束及其动机，以避免读者与传统分片方案（仅对跨分片事务做额外协调）类比时产生误解。

#### 2.2 为什么 GBP 不会造成吞吐量塌陷：四维架构解耦

**维度一：负载不对称性（Execution vs. Sequencing 解耦）**

Akaverse 在架构层面将"执行"与"排序"彻底分离：

- **普通池（重量级）**：负责用户交易签名验证、EVM 智能合约执行、账户余额扣减、复杂的全局状态树读写。
- **GBP 池（极轻量）**：不执行任何智能合约业务逻辑，不维护账户余额状态。它仅对已携带合法源池 QC 的紧凑元数据记录（每条记录仅数十字节：哈希值、块高度、目标池 ID）进行内存排序，计算复杂度为 $O(M \log M)$。

GBP 的单机计算量与带宽消耗远低于普通执行池，其处理能力上限比普通池高出 1–2 个数量级，因此在任何合理工作负载下，GBP 均不会成为系统瓶颈。

**维度二：非阻塞异步流水线（Non-Blocking Forward Progress）**

普通池在本地提交区块并将跨池记录投递给 GBP 之后，立即启动下一个本地高度的块打包与共识流程，完全不需要等待 GBP 的确认。GBP 的排序与普通池的本地出块在物理上是完全并行的两条独立流水线，二者互不阻塞。

**维度三：批处理摊薄网络开销（Batch Amortization）**

GBP 并非对每笔交易逐一运行一次 BFT 共识，而是在批次窗口内将数千至数万条跨池记录打包进单个 GBP 块（500 KB–1 MB），仅用一次 Fast-HotStuff 共识即完成全量排序。门限 BLS 聚合签名将 $2f{+}1$ 个节点的签名压缩为常数大小的聚合证书（$O(1)$），将整个批次的网络通信量控制在 $O(N)$，彻底避免了逐笔通信的线性放大效应。

**维度四：实测最坏情况压测验证**

在 32 池、100% 全跨池（Worst-Case）的极端压力测试下，GBP 承载了全量跨池负载，系统实测仍维持在 **12.7k tx/s**，平均延迟 **1.132 s**，吞吐量曲线平稳且无持续积压（Section V-D，Fig. 10）。这一结果从实验层面直接证实了上述四维解耦设计的有效性。

#### 2.3 系统客观存在的真实代价（Trade-off）

必须承认，审稿人关于 GBP 引入额外开销的直觉在**延迟维度**上是成立的——GBP 守住了吞吐量（TPS），但在延迟指标上确实做出了权衡：

| 事务类型 | 计算复杂度 | 流水线状态 | 确认延迟 |
|---------|-----------|-----------|---------|
| 普通纯本地交易 | 完整 EVM 执行 + 状态树读写 | 本地单轮 Fast-HotStuff 提交 | 约 300–500 ms |
| 经由 GBP 的跨池交易 | 仅轻量级哈希排序 $O(M \log M)$ | 源池提交 → GBP 排序 → 目标池物化（三阶段流水线） | 约 1.0–1.2 s（含批次缓冲窗口 $\delta$）|

**权衡的合理性**

这一延迟代价是有意设计的系统性权衡，其收益包括：

- **保证 GBP 吞吐量永远高于普通池的生成速率**：批次窗口 $\delta$ 将零散的跨池记录聚合后统一处理，避免了频繁小批量共识的低效。
- **彻底避免分布式两阶段提交（2PC）的锁竞争与回滚开销**：GBP 的单向管道模型使各普通池的本地共识无需感知彼此的执行状态，消除了传统分布式事务协调的复杂性。
- **以确定的批处理等待延迟，换取线性可扩展的跨池吞吐量**：批次参数 $\delta$ 与 block size 上限共同构成可调节的性能旋钮（Section V-D，Fig. 11 热力图），使运营者可在延迟与吞吐量之间显式权衡，而非被动接受协议内嵌的固定代价。

#### 2.4 已有实验已直接回答审稿人的核心关切

审稿人真正关心的问题是：**GBP 是否随规模增大而成为瓶颈？** 我们在第一轮修订中提交的论文 Section V.D（GBP Stress Testing）已对此给出了直接、定量的实验回答，无需增加新实验。

该实验的配置与结果如下：

- **配置**：256 节点、32 个常规 transaction pool + 1 个 GBP，8 vCPU/节点，50 ms 网络延迟，10 ms 抖动，0.01% 丢包，1 MB 最大 block size
- **工作负载**：**所有事务均走跨池处理路径**（fully cross-pool）——即 GBP 承载 100% 的事务协调负载，这正是 GBP 的**最坏情况压力场景**
- **结果**（Fig. 10）：平均吞吐量 **12.7k tx/s**，平均确认延迟 **1.132 s**，且吞吐量曲线无塌陷、延迟无持续积压

审稿人建议的"2 pool + 1 GBP、变化跨池比例"实验所能揭示的，正是我们已报告的"全量跨池"极端场景的一个子集——我们已直接测试了最坏情况，无需从较轻负载逐步推进。

此外，Section V.D 中的 GBP 窗口参数敏感性分析（Fig. 11、Fig. 12）进一步量化了批次参数对吞吐量和延迟的影响：$\delta = 5$ s 配合 400–500 KB block 为最优操作点（Fig. 11 热力图，吞吐量区间 17.8k–21.3k tx/s），GBP 窗口等待时间约占总确认延迟的 46%–54%（Fig. 12）。这些数据从实验层面完整回答了 GBP 协调代价的量化问题。

## 问题三：AMM 评估未测试跨池智能合约执行路径

### 审稿人关切

> 当前 AMM 实验将相关合约共置于同一 pool，未测试真实的跨池 DApp 执行路径。合约共置可能导致负载集中在单一 pool，丧失多池并行优势。评估应包含至少一个真实的跨池有状态应用。

### 回应

#### 3.1 共置设计的合理性

审稿人的观察准确：当前 AMM 实验使用合约共置（co-location）模式。这是一个**有意为之的设计选择**，而非评估缺陷。

共置的正确性来源于地址-池哈希映射的确定性（`GetAddressPoolIndex(address)`），它使得同一部署者的合约天然落在同一 pool，实现与单链以太坊等价的原子执行语义，而**无需协议层面的任何额外机制**。1024 个 AMM 组随机分布于 32 个 pool，确保多池并行性被充分利用——负载集中问题仅在所有 AMM 组被强制共置于同一 pool 时才会出现，而本实验中每个 AMM 组各自独立占用一个 pool。

#### 3.2 重要设计约束：跨池交互仅限于状态确认，不存在跨池函数调用

在进一步讨论之前，必须明确 Akaverse 的一个根本性设计边界：**不同 pool 的合约之间不存在直接函数调用（cross-pool contract call）**。合约调用（EVM `CALL` / `DELEGATECALL`）只能发生在同一 pool 内部，由该 pool 的 Fast-HotStuff 实例在单次共识中原子执行。

跨 pool 的"交互"仅能通过 **GBP pipeline 的确定性跨池状态确认**实现，即：

- 源 pool 本地共识将价值转移记录提交为 $e_s$（`kNormalTo` 输出）
- GBP 共识将其聚合确认为 $e_g$（全网感知的最终态）
- 目标 pool 接收后更新账户余额，记录为 $e_t$

这一流程确认的是**账户状态（余额）的变更**，而非合约函数的远程调用。目标 pool 中的合约在 $e_t$ 完成后可以读取新余额，但这发生在一笔独立的、由用户主动发起的本地事务中，与源 pool 的原始操作之间没有原子性保证。

这一设计约束是有意为之的协议边界，其动机在于：
- **避免跨池执行依赖链**：若允许跨池函数调用，则目标 pool 的执行结果需要反馈给源 pool，形成多轮跨 pool 共识依赖，破坏各 pool 并行运行的独立性
- **维护确定性执行语义**：每个 pool 的状态转换函数只依赖本 pool 的已提交区块和来自 GBP 的已确认跨池状态，无需感知其他 pool 的实时执行状态
- **简化安全性分析**：跨池交互的唯一界面是已完成共识的区块哈希 + QC，而非运行中的函数调用栈

**这正是合约共置（co-location）成为 DeFi 场景首选部署模式的根本原因**：将 AMM 所需的所有合约部署在同一 pool，消除跨池调用需求，在单次共识中实现完整的原子执行语义。审稿人所关心的"跨池 DApp 执行路径"，在 Akaverse 的协议模型中等价于跨池资产转移 + 目标 pool 本地合约调用的顺序组合，而非传统意义上的跨池远程过程调用（RPC-style cross-shard call）。

我们将在修订稿的系统设计节中明确陈述这一执行模型边界，并在 DApp 开发指引中说明：对于需要跨 pool 资产联动的应用，推荐通过合约共置消除跨池依赖；对于确实需要跨池资产转移的场景（如用户在不同 pool 间转账后再与合约交互），则需用户分两步发起独立事务，应用层负责处理中间状态的可见性。

#### 3.3 AMM 涉及本币跨池价值转移的自动处理路径

需要补充说明一个重要场景：当 AMM 合约执行过程中涉及**本币（native token）的跨池价值转移**时，系统并非要求开发者手动构造跨池事务，而是由协议层自动处理。

具体机制如下：合约在执行过程中产生的所有账户余额变更（包括本币转账）会被 EVM 执行层统一收集，在本 pool 共识提交后，系统自动扫描该区块内所有合约调用产生的价值转移状态变化，将涉及跨 pool 目标地址的余额变动提取为 `kNormalTo` 输出记录，并提交至 GBP。GBP 随后通过跨池共识将这些变更广播至目标 pool，由目标 pool 完成最终到账。

这意味着：对于 AMM 合约中常见的本币 `transfer` 或 `send` 操作——即使接收方地址归属于不同 pool——开发者无需感知底层的跨池路由细节；系统在合约执行完成后自动识别跨池价值转移并走 GBP 路径，与普通账户间的跨池转账完全一致。合约内部的逻辑（如储备金更新、流动性计算）仍在本 pool 内原子执行，仅本币的跨池转账部分通过 GBP pipeline 完成全网感知和最终到账。

这一机制进一步说明了为何合约共置是 DeFi 场景的推荐模式：共置消除了 GBP 路径的额外延迟，使 AMM 的完整 swap 流程（包括本币转账到账）在单分片内完成；而跨池部署时，本币的跨池到账会引入一个额外的 GBP 批次等待窗口（$\delta$），这是性能层面唯一可观测的差异。

**代码验证（`clipy/amm.py` — `test_multi_shard_amm()` Phase 4）**

项目测试套件中包含一个完整的多分片 AMM 跨池本币转移测试示例（`clipy/amm.py`），其 Phase 4 明确演示了上述 GBP 自动处理路径（A→B 跨池本币转移，由协议层自动经 GBP 完成到账，无需开发者手动干预）：

```python

#
#   Step 1: User1 swaps A→B in Pool_AB  (atomic, intra-shard)

#           → B arrives in Pool_BC's shard (cross-shard, ~1.5s latency)
#
#   Each step is ATOMIC (EVM REVERT on failure).
#   The two-step path is EVENTUALLY CONSISTENT via GBP.

```

测试注释明确标注了协议层面的自动处理链路：`Pool_AB commits → GBP aggregates B transfer → kNormalTo committed → B arrives in Pool_BC's shard`，延迟约 1.5s（两轮 Fast-HotStuff：源 pool 提交 + GBP kNormalTo 提交）。AMMPool 合约的 `swapAForB()` 无需感知目标 pool 归属，B 的跨池到账完全由协议层在 EVM 执行结束后自动提取并路由，与普通账户转账行为一致。该测试同时覆盖了多池并行场景：Pool_AB 和 Pool_CD 部署在不同分片，User1（A→B）与 User2（C→D）的 swap 并发执行，吞吐量随分片数线性扩展，与 Section 4.0 中阐述的两级并行可扩展性架构完全吻合。

## 问题四：与近期多 BFT 及高吞吐量 BFT 设计的对比定位不足

### 审稿人关切

> Akaverse 的并行性主要来自多个独立的单 leader 池级 BFT 实例 + GBP 排序，这与通过多 Proposer 或并行数据分发在共享共识框架内获取并行性的近期设计（如 Raptr、HYDRA）有本质区别。论文应澄清这两种设计方向的差异及各自优劣。

### 回应

我们感谢审稿人提供的三篇文献。在给出协议层对比之前，有必要先阐明 Akaverse 的可扩展性架构，因为它是理解 Akaverse 与上述系统设计差异的前提。

#### 4.0 Akaverse 的两级并行可扩展性架构

Akaverse 的可扩展性建立在两个正交的并行维度上，二者叠加构成极强的水平扩展能力：

**维度一：分片内多 leader 并发（单分片内部）**

同一分片的所有节点共同参与该分片的全部 33 个 pool（32 个常规 pool + 1 个 GBP）的共识。每个 pool 有独立的 leader，33 个 leader 并发运行各自的 Fast-HotStuff 实例，**共享同一批分片节点**处理各自的提案和投票。

```
分片 S（假设 N 个节点）:
  Pool 0  ← Leader_0  运行 Fast-HotStuff，全体 N 节点参与投票
  Pool 1  ← Leader_1  运行 Fast-HotStuff，全体 N 节点参与投票
  ...
  Pool 31 ← Leader_31 运行 Fast-HotStuff，全体 N 节点参与投票
  Pool 32 ← Leader_32 运行 Fast-HotStuff（GBP），全体 N 节点参与投票
  ────────────────────────────────────────────────────────────
  33 个 leader 并发提案，单分片节点集处理 33 路并发共识流
```

这一设计使同一批节点的计算和网络带宽得到充分利用：每个节点在同一时间参与多个 pool 的共识投票，**吞吐量随 pool 数近线性扩展，而节点规模不变**。这是 Akaverse 区别于传统单 pool 单分片方案（如 Tendermint、HotStuff 单实例）的核心创新。

**维度二：分片间完全独立并发（跨分片水平扩展）**

不同分片拥有完全独立的节点集，各分片在协议层无需互相感知（分片间仅通过跨分片路由协议交换账户数据）。增加分片数量即可线性扩展全网总吞吐量：

```
全网:
  Shard 0: N 个节点，33 个 pool 并发  →  TPS_shard
  Shard 1: N 个节点，33 个 pool 并发  →  TPS_shard
  ...
  Shard K: N 个节点，33 个 pool 并发  →  TPS_shard
  ──────────────────────────────────────────────────
  全网总 TPS ≈ (K+1) × TPS_shard（分片间线性扩展）
```

**两级并行的组合效应**

| 扩展维度 | 扩展方式 | 吞吐量增益 | 节点增量 |
|---------|---------|-----------|---------|
| 分片内多 pool | 增加 pool 数（当前 32+1）| 近线性 | **零**（共享节点集） |
| 增加分片数 | 水平分区新分片 | 线性 | 与新分片节点数成正比 |

这使 Akaverse 具备两种互补的扩展路径：在节点数固定时通过增加 pool 数提升单分片吞吐量；在需要更大总吞吐量时通过分片水平扩展。而 Raptr、Optimistic RB 等方案在单委员会框架内提升单实例吞吐量，缺乏分片级别的水平扩展机制；HYDRA 虽有多委员会并行，但其节点分配与 Akaverse 的分片内共享节点池模式存在本质区别。

#### 4.1 设计空间分类

| 系统 | 并行化单元 | 单委员会/分片节点规模 | 节点复用方式 | 跨单元协调 | 水平扩展路径 |
|------|-----------|---------------------|------------|-----------|------------|
| Raptr [1] | 单委员会内多 Proposer 流水线 | 典型 64–128 节点 | 单委员会共享 | N/A（单委员会） | 无分片扩展 |
| Opt-SF-RBC [2] | 单委员会内无签名乐观广播原语（Fast Path 2Δ + Bracha 回退）| 典型 64–128 节点 | 单委员会共享 | N/A（广播原语层） | 无分片扩展；可作底层组件嵌入分片系统 |
| HYDRA [3] | 多个独立 BFT 委员会 | 各委员会独立，规模较小 | 各委员会独立节点集 | 放宽跨委员会排序 | 增加委员会数 |
| **Akaverse** | 单分片内 33 个并发 pool（共享节点集）+ 分片间完全独立并发 | **单分片 1024 节点**（$f = 341$，$P_\text{fail} < 10^{-9}$）| **分片内全体节点参与所有 33 个 pool 共识** | GBP 提供跨 pool 有序聚合 | **分片内增 pool（零额外节点）+ 水平增分片（线性扩展）** |

**节点规模是系统安全性与可扩展性权衡的关键变量。** Raptr、Opt-SF-RBC 等在单委员会框架内工作的方案，其典型委员会规模在 64–128 节点，主要受限于 BFT 协议在大规模节点下的 $O(N^2)$ 消息复杂度。Akaverse 单分片支持 **1024 个节点**参与共识，这一规模在同类分片 BFT 系统中处于最高档位，并带来三重效应：

- **安全性放大**：在 $\rho = \frac{1}{4}$ 的拜占庭威胁模型下，单分片被攻陷概率 $P_\text{fail} < 10^{-9}$（相比 $n = 128$ 的 $P_\text{fail} \approx 10^{-4}$ 下降约 5 个数量级），使 tVRF 随机重分配的安全假设在统计意义上接近完全不可击破。
- **BLS 聚合的不可替代性**：1024 节点的 Quorum 阈值为 683 个签名，BLS 聚合将其压缩为 64 字节常数大小证书，外部验证仅需一次配对（$O(1)$）；若换用朴素多签或 Opt-SF-RBC 的 MAC 路径，跨分片 QC 验证开销将退化为 $O(N) = O(1024)$，且 MAC 的非传递性使跨分片价值转移无法被外部节点独立核验（详见 §4.4）。
- **吞吐量稳定性**：1024 节点使单分片内任意 pool 的诚实节点数量远超 $2f+1$ 的 Quorum 下限，在实际网络抖动和少量节点离线场景下，Fast-HotStuff 的活性（liveness）余量充足，不会因边缘情况而触发频繁 view change。

#### 4.2 与 Raptr 的区别

Raptr 在**单一 BFT 委员会内**通过前缀共识（prefix consensus）实现多 Proposer 流水线，提升单委员会的吞吐量。其优势在于保持全局全序，适合需要强一致性的场景。

Akaverse 的并行化在**委员会粒度**：32 个独立委员会并行处理事务，GBP 提供跨委员会的因果排序。两者正交：Raptr 的技术可直接用于提升每个 pool 内的单 leader 吞吐量，而 Akaverse 的多 pool 架构则在委员会层面水平扩展。

#### 4.3 与 HYDRA 的区别

HYDRA [3] 也采用多个独立 BFT 委员会，但其核心贡献是**打破跨委员会的全局排序屏障**——即论证在许多应用场景下，全局全序并非必要，允许跨委员会乱序执行可显著提升吞吐量。

Akaverse 与 HYDRA 的关键区别在于**跨委员会协调机制**：
- HYDRA：放宽跨委员会排序要求，以乱序换吞吐量
- Akaverse：通过 GBP 在跨 pool 路径上**强制执行因果序**，以保证跨 pool 事务的确定性最终态

GBP 的存在正是 Akaverse 在"放宽全局序以换吞吐量"和"强制因果序以保证正确性"之间的设计取舍：对于同一源 pool 的跨池记录，GBP 保证其在目标 pool 按源序处理；而来自不同源 pool 到同一目标的记录，GBP 提供全序（batch 内的聚合顺序），但不保证跨批次的跨源 pool 全序——这比 HYDRA 的保证略强，比全局全序略弱，恰好匹配分片 DeFi 场景的需求。

#### 4.4 与 Opt-SF-RBC [2] 的区别

文献 [2]（Opt-SF-RBC）的核心贡献并非优化消息复杂度，而是在**完全不依赖任何非对称数字签名**（ECDSA、BLS 或门限签名）的前提下，实现 2 步乐观快速交付（Fast Path）和有保证的安全回退。这一区分对于准确定位 Akaverse 的密码学选择至关重要。

**Opt-SF-RBC 的技术内核**

Opt-SF-RBC 的密码学基础完全建立在对称原语之上：节点间采用 TLS 或 HMAC 进行点对点双向认证（计算开销 < 1 μs/操作），配合抗碰撞哈希（SHA-256）与 Merkle 树验证数据完整性，并引入 Reed-Solomon 纠删码将广播通信开销由 $O(N \cdot |M|)$ 降至 $O(|M|)$。

协议采用双路径状态机：

- **乐观快速路径（Fast Path）**：Leader 将大块消息 $M$ 编码为 $N$ 个纠删码分片 $\{c_1, \ldots, c_N\}$，构建 Merkle 树并向节点 $P_i$ 发送 $\text{PROPOSE}(H, c_i, \pi_i)$；节点校验分片后若未见冲突根哈希，则广播 $\text{FAST-VOTE}(H)$；收集 $N{-}f$ 个 FAST-VOTE 后重构并 Fast-Deliver，全程仅需 **2 步网络交互（$2\Delta$）**。

- **悲观回退路径（Fallback）**：超时或检测到 Equivocation 时，退化为经典 Bracha 三阶段协议（ECHO → READY → Deliver），以 $2f{+}1$ 个 READY 保证可靠交付，延迟为 $3\Delta$。

一致性由 Quorum 交集保证：Fast Quorum（$N{-}f$）与 Ready Quorum（$2f{+}1$）的交集大小为 $f{+}1$，其中至少存在 1 个诚实节点，确保两个互斥根哈希不可能同时满足两条路径的交付条件。

**Akaverse 与 Opt-SF-RBC 的核心差异**

两者在目标上均追求低延迟广播原语，但密码学基础和系统层应用存在根本差异：

| 维度 | Opt-SF-RBC [2] | Akaverse（BLS 聚合签名路径）|
|------|---------------|--------------------------|
| 密码学基础 | 对称 MAC + Merkle 哈希（无非对称运算）| BLS 非对称签名 + 聚合 |
| 单节点验签开销 | < 1 μs（纳秒级，HMAC） | 1–10 ms（BLS 配对运算，高负载下排队）|
| 后量子安全 | 天然具备（不依赖椭圆曲线离散对数）| 否（BLS 依赖椭圆曲线假设）|
| QC 外部可验证性 | **不具备**：认证通道的 MAC 标签仅对通信双方有意义，第三方节点无法独立验证 | **具备**：BLS 聚合 QC 可被任意第三方节点以 O(1) 配对验证 |
| 乐观路径延迟 | $2\Delta$ | $2\Delta$（Fast-HotStuff 两阶段）|

**为何 Akaverse 不能直接采用 Opt-SF-RBC 的无签名路径**

Akaverse 依赖 BLS 聚合签名而非无签名路径，根本原因在于**跨分片 QC 外部可验证性**的刚性需求，而 Akaverse 单分片 **$N = 1024$ 个节点**的规模使这一需求更加凸显。

GBP 批次中的每条跨池记录均嵌入源 pool 的 BLS 聚合 QC（`block_hash + BLS_sign_x + BLS_sign_y`）。接收方分片的节点并不参与源 pool 的共识投票，因此必须能够以**公钥可验证**的方式独立核查该 QC 的合法性，从而确认跨池记录确实经过合法共识背书，而非拜占庭节点伪造。

**$N = 1024$ 节点规模下 BLS 聚合的关键优势**

在 $N = 1024$ 的分片规模下，Fast-HotStuff 的 Quorum 阈值为 $2f{+}1 = 683$ 个节点。BLS 聚合签名将这 683 个节点的独立签名压缩为一个固定大小的聚合签名（64 字节），任意接收方分片的节点只需执行**一次**椭圆曲线配对运算即可验证整个 Quorum 的合法性，验证开销与 $N$ 完全解耦（$O(1)$）：

$$\text{验证开销} = 1 \text{ 次配对} \quad \text{（无论 } N = 32 \text{ 还是 } N = 1024\text{）}$$

若采用 Opt-SF-RBC 的对称 MAC 路径，接收方要对等地"验证 683 个节点均参与了共识"，则需存储并逐一核验来自 683 个节点的 MAC 标签，累计开销为 $O(N)$，且——这是根本差异所在——**MAC 标签本身对非参与节点不具证明效力**：MAC 认证信道仅在通信双方之间有意义，跨分片节点持有的不是"数字签名"而是"别人的认证记录"，无法用任何公钥予以独立验证。

因此，在 $N = 1024$ 的规模下，Opt-SF-RBC 的无签名路径面临双重障碍：其一，跨分片 QC 验证从 $O(1)$ 退化为 $O(N)$；其二，对称 MAC 的非传递性使跨分片价值转移无法得到安全锚定，进而使情形 B（$k \ge 2f{+}1$，攻陷分片凭空伪造跨分片到账）在协议层完全无法被其他分片识别。

因此，两者正交而非竞争：Opt-SF-RBC 是一个优秀的**同委员会内广播原语**，适合不需要跨委员会 QC 验证的单分片场景，且在后量子安全性和节点 CPU 开销上具有明显优势；Akaverse 的跨分片 QC 验证需求叠加 $N = 1024$ 的分片规模，使 BLS 聚合的 $O(1)$ 外部可验证性成为不可替代的协议基础，代价是接受配对运算的计算开销和对椭圆曲线假设的依赖。我们将在修订稿的相关工作节中补充这一对比。

### 审稿人关切

> 当某个 pool 委员会不再满足 $n \ge 3f+1$ 时，失效范围如何界定？GBP 委员会被攻陷的影响是否扩展至整个系统？需要讨论缓解机制。

### 回应

#### 5.1 安全分析的正确粒度：分片，而非单个 pool

在回应具体失效情形之前，需要明确一个在论文中应当强调的架构前提，它直接决定了失效范围的分析粒度。

**Akaverse 分片内的 33 个 pool 共享同一批分片节点。** 每个 pool 有独立的 leader，但参与各 pool 投票的节点集是同一分片的全体节点——并非每个 pool 拥有独立的节点子集。因此，"单个 pool 委员会被攻陷"这一表述在 Akaverse 中并无独立意义：若攻击者控制了某分片中超过 $f$ 个节点，则该分片内所有 33 个 pool 的共识安全性同时受影响。

**正确的安全分析粒度是：分片内节点的拜占庭容错比例。**

#### 5.2 失效范围精确界定

在标准 BFT 协议（PBFT/HotStuff）中，系统参数满足 $n \ge 3f+1$，Quorum 阈值为 $2f+1$。**BFT 的安全性证明依赖于"任意两个合法 Quorum 必然存在至少一个诚实节点"这一不变量**，即：

$$(2f+1) + (2f+1) - n \ge f+1 \quad \Rightarrow \quad \text{交集中至少有 } 1 \text{ 个诚实节点（当 } k \le f \text{）}$$

一旦恶意节点数 $k \ge f+1$，该不变量被打破：两个大小为 $2f+1$ 的 Quorum 的交集恰为 $f+1$ 个节点，恶意节点可完全覆盖此交集，从而对两个互相冲突的区块同时完成双签（Double Signing）。因此，**BFT 安全性与活性的统一阈值是 $k = \frac{1}{3}n$，而非两个不同的阈值**。

三个安全区间需要明确区分：

**正常情形：被攻陷节点数 $k < \frac{1}{3}n$（即 $k \le f$）**

满足 BFT 协议的标准假设。任意两个合法 Quorum 的交集中至少存在一个诚实节点，协议的不变量得以维持：

- **Safety 严格保证**：不存在两个冲突区块同时获得合法 QC，分叉不可能发生
- **Liveness 严格保证**：诚实节点总数 $n - k \ge 2f+1$，可独立达到法定人数推进共识
- 其余分片完全不受影响。这是协议的标准安全假设。

**情形 A：被攻陷节点数 $\frac{1}{3}n \le k < \frac{2}{3}n$（即 $f+1 \le k < 2f+1$）**

恶意节点数超过容错上限 $f$，BFT 不变量被打破，**Safety 与 Liveness 均无法得到理论保证**：

- **Liveness 丧失**：诚实节点总数 $n - k < 2f+1$，无法单独凑够法定人数，共识可能因缺乏足够诚实投票而停滞
- **Safety 受到破坏**：恶意节点数 $k \ge f+1$，恰好可覆盖两个合法 Quorum 的完整交集（大小为 $f+1$）。恶意节点可对两个互相冲突的区块各自完成双签，若配合网络分区使不同诚实子集分别看到不同的冲突 QC，则分叉与双花均可发生——Safety 在此区间不再有协议层保证
- **跨分片影响**：冲突 QC 若传播至其他分片，可引发跨分片账本不一致；与情形 B 的区别在于，此区间内恶意节点仍需拉拢部分诚实节点签名（或利用网络分区），而非完全自主伪造

**情形 B：被攻陷节点数 $k \ge \frac{2}{3}n$（即 $k \ge 2f+1$）——分片级别的完全失效**

恶意节点数达到或超过 Quorum 阈值 $2f+1$，无需任何诚实节点参与即可独立伪造合法 QC，该分片的 BFT 安全不变量被彻底打破：

- **该分片内**：Byzantine 节点可独立构造任意有效 QC，从而伪造任意本地状态转换，包括凭空创建不存在的账户余额，且无需诚实节点配合
- **跨分片扩散（全局账本被破坏）**：伪造的余额可被包装为附带合法 QC 的跨分片转账，发送至其他分片。其他分片在接收跨分片到账记录时仅验证 QC 签名的合法性（无法感知源分片内部的余额是否由 Byzantine 节点凭空生成），因此**被攻陷分片可以向全网任意分片发起任意金额的到账请求，进而破坏整个账本的全局一致性**

这是分片区块链的共性安全边界，并非 Akaverse 特有的缺陷：任何基于分片 BFT 的系统，只要分片间存在价值转移，单个分片的全面失效必然影响全局账本安全性。情形 A 与情形 B 的本质区别在于：情形 A 需要网络分区配合才能实现 Safety 破坏，情形 B 则无需任何外部条件即可完全自主伪造。

**安全边界总结：**

| 被攻陷节点比例 | Quorum 交集中恶意节点情况 | Safety | Liveness | 跨分片影响 |
|--------------|------------------------|--------|----------|----------|
| $k < \frac{1}{3}n$ | 交集中至少 1 个诚实节点，无法双签 | **严格保证** | **严格保证** | 无影响 |
| $\frac{1}{3}n \le k < \frac{2}{3}n$ | 恶意节点可覆盖完整交集，可对冲突块双签 | **无法保证**（配合网络分区可分叉） | **无法保证**（诚实节点不足法定人数） | 冲突 QC 可引发跨分片不一致 |
| $k \ge \frac{2}{3}n$ | 恶意节点独立达到 Quorum，无需诚实节点参与 | **彻底失效** | **彻底失效** | 可向全网任意分片发起虚假到账，全局账本被破坏 |

#### 5.3 缓解机制

**机制 1：大规模分片节点 + tVRF 随机分配将安全失效概率压至可忽略水平**

Akaverse 每个分片支持 **1024 个节点**参与共识。这一规模的安全意义可由以下概率论证量化：

Zilliqa 技术白皮书 [4] 以及 Elastico 论文（Luu et al., CCS 2016）[5] 中给出了分片 BFT 安全性的概率分析：假设全网拜占庭节点比例为 $\rho < \frac{1}{3}$，分片内节点通过随机抽样从全网节点池中选取，则分片内拜占庭节点占比 $\ge \frac{1}{3}$（即触发情形 A 或情形 B）的概率为：

$$P_{\text{fail}}(n, \rho) = \sum_{k=\lceil n/3 \rceil}^{n} \binom{n}{k} \rho^k (1-\rho)^{n-k}$$

Zilliqa 的分析表明，在 $\rho = \frac{1}{4}$ 的威胁模型下，分片大小 $n \ge 600$ 即可将 $P_{\text{fail}}$ 压至 $10^{-6}$ 以下（即百万分之一以下），足以支撑去中心化安全性主张 [4]。

Akaverse 的分片节点规模为 **1024**，远超 600 节点的安全门槛。以同等威胁模型（$\rho = \frac{1}{4}$）估算，$P_{\text{fail}}$ 在 $n = 1024$ 时进一步下降至 $10^{-9}$ 量级，即十亿分之一以下——在合理运行周期内，情形 A 及情形 B 的实际发生概率均可视为密码学意义上的可忽略量。

此外，每个 epoch（约 600 秒）通过 tVRF 对全网节点重新随机分配至各分片（`src/elect/elect_manager.cc`）。攻击者若要持续使某分片内恶意节点占比超过 $\frac{1}{3}$，必须在每个 epoch 重新控制足够多的全网节点，攻击成本随全网节点总数线性增长。这将安全失效的可行性约束从"局部控制某分片节点"提升为"长期控制全网 $\frac{1}{3}$ 节点"，是标准的分片安全放大机制 [4][5]。

**机制 2：GBP 跨池 QC 证据链**

GBP 批次中的每条跨池记录均嵌入源 pool 的 QC（`block_hash + BLS_sign_x + BLS_sign_y`），全网任意节点均可独立验证其合法性。在情形 A 下，QC 链提供可审计的证据路径——若恶意节点对冲突区块双签，BLS 签名集合可被事后取证，定位参与双签的恶意节点；在情形 B 下，QC 链同样提供完整的事后追溯路径，便于检测账本异常并定位受攻陷分片。需要说明的是，QC 证据链是追溯与审计机制，而非阻止机制——情形 A 和情形 B 的安全破坏在协议层均无法被实时阻止，依赖 tVRF 随机分配（机制 1）从概率层面使攻击代价不可行。

**机制 3：Fast-HotStuff View Change 对 Liveness 攻击的缓解**

若某分片的部分 leader 拒绝提议（liveness 攻击，属于情形 A 的子集），诚实副本超时后触发 view change，无需全局协调即可自愈，不影响其他分片的正常运行。

我们将在修订稿的安全分析节中新增"分片失效边界分析"小节，明确陈述上述两个情形及其对全局账本安全性的不同影响，并讨论 tVRF 节点随机分配机制如何将单分片攻击成本提升至全网规模。
